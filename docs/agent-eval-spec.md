# `agent-eval` — 1–2 Day Build Specification

Status: implementation-ready MVP  
Implementation language: Go  
MVP task language: Go  
Form factor: local CLI

## 1. Purpose

`agent-eval` evaluates an AI coding agent on a small, fixed suite of programming tasks. For each attempt, it prepares a fresh workspace, lets the agent inspect and edit files and run approved checks, records a structured trace, freezes the submitted files, and independently grades the result.

The first release contains three to five Go tasks and runs directly on the local machine. The core contracts are language-neutral so later versions can add Python, TypeScript, Rust, Java, container execution, hosted workers, a web UI, and persistent artifact storage without replacing the agent loop or grading model.

## 2. Product principles

1. Executable checks are the authority for correctness.
2. The agent never chooses arbitrary commands to execute.
3. Hidden tests are unavailable until the submitted workspace is frozen.
4. Task failure, agent failure, setup failure, and grader failure are different outcomes.
5. Correctness, code quality, and efficiency are reported separately.
6. Every attempt is diagnosable through manifests, hashes, environment metadata, traces, and final patches.
7. The local MVP is for trusted task code. Strong isolation is a future execution backend.

## 3. Scope

### In scope

- A local Go CLI with `doctor`, `list`, `run`, and `report` commands.
- Three to five versioned Go tasks stored in the repository.
- A balanced suite containing code generation, bug repair, and feature-extension work.
- One primary coding agent per task.
- An OpenAI-compatible model adapter configured through flags and environment variables.
- Controlled tools for listing, reading, searching, writing, and patching files.
- A named `run_check` tool that runs checks generated by the trusted Go profile.
- One fresh temporary workspace per task attempt.
- Hidden-test overlays installed only after the agent finishes.
- Deterministic grading using compilation, tests, static checks, and task-specific policies.
- Mechanical code-quality checks such as formatting and `go vet`.
- Structured JSONL traces and machine-readable results.
- Toolchain and dependency preflight checks before model use.
- Task-local build and dependency caches where practical.
- Workflow, budget, and trace types that can represent primary and child agents.

### Explicitly out of scope for the MVP

- Web UI or HTTP service.
- Docker, containers, VMs, or remote execution.
- Databases; artifacts are stored on the filesystem.
- Strong execution isolation for hostile task code.
- Support for task languages other than Go.
- Agent-controlled shell access or package installation.
- Dynamic task downloads, public leaderboards, distributed workers, or hosted execution.
- User accounts, authentication, billing, or shared tenancy.
- An LLM code-quality judge as a required grading component.
- Peer-to-peer agents, recursive delegation, or concurrent writes from multiple agents.

## 4. User workflow and event sequence

```text
agent-eval doctor --suite tasks/suite.yaml
agent-eval list   --suite tasks/suite.yaml
agent-eval run    --suite tasks/suite.yaml --out .eval/runs
agent-eval report .eval/runs/<run-id>
```

`doctor` verifies the local toolchain, dependencies, generated grader plan, and writable directories without contacting the coding model unless explicitly requested.

For each selected task, `run`:

1. Loads and validates the suite and task manifests.
2. Verifies required programs and toolchain versions.
3. Creates a fresh workspace from the task's `starter/` directory.
4. Prepares locked dependencies and task-local caches.
5. Runs environment verification and compile-only checks.
6. Starts the primary agent with the prompt and allowed tools.
7. Executes validated tool calls until the agent finishes or a budget is exhausted.
8. Freezes the final workspace so the agent can no longer modify it.
9. Copies hidden-test overlays into their declared workspace paths.
10. Runs all final grader checks independently of the agent.
11. Runs mechanical code-quality checks.
12. Calculates correctness and diagnostic scores.
13. Saves the trace, result, environment fingerprint, and final patch.
14. Continues to the next task even if this task is unsolved.
15. Prints an aggregate summary.

The agent cannot see hidden-test files or hidden-test output during steps 1–8. Once grading begins, it cannot react to the result.

## 5. Functional requirements

### R1 — Task discovery and validation

- Load a suite YAML file that names three to five task IDs. Each ID maps by convention to `tasks/<task-id>/`.
- Each shipped MVP task contains `task.yaml`, `prompt.md`, `starter/`, `hidden/`, and `reference/` at conventional paths.
- Reject duplicate IDs, missing files, invalid budgets, unknown schema versions, and paths escaping the task or suite root.
- Read the language and toolchain requirement from the suite. The MVP accepts only `language: go`.
- Expand the small author-facing manifests through the built-in Go profile into a normalized internal plan, then validate every generated command, parser, path, and policy before contacting a model.
- `list` prints task ID, title, kind, tags, language, and time budget.

### R2 — Environment checks and preparation

- `doctor` checks the tools, versions, dependency files, writable directories, and commands produced by the suite's language profile.
- `run` automatically repeats the task-relevant checks before model use.
- A missing compiler, incompatible version, failed dependency download, or invalid grader is a `SETUP_ERROR` or `GRADER_ERROR`, not an unsolved task.
- Preparation and verification commands come from the built-in Go profile. Internally they use argument arrays and never use shell parsing.
- Dependencies are pinned by `go.mod` and `go.sum` in the MVP.
- Prepare Go dependencies with `go mod download` and verify them with `go mod verify`.
- Use evaluator-owned `GOMODCACHE`, `GOCACHE`, and temporary directories where practical.
- After preparation, agent checks and grading use `GOPROXY=off` so unexpected module fetching fails.
- Record operating system, architecture, tool versions, manifest hash, starter hash, and dependency-file hash in `run.json`.
- Do not count environment preparation against the agent's budget; record it separately.

The local backend cannot fully prevent arbitrary network or host access by code executed during tests. Tasks must therefore be trusted in the MVP.

### R3 — Reproducible workspace creation

- Copy `starter/` into a new task workspace.
- Never edit the canonical starter fixture.
- Exclude `.git`, build artifacts, hidden graders, and evaluator-owned files.
- Compute a content hash of the canonical starter before the run and verify it is unchanged afterward.
- Support `--keep-workspaces`. By default, preserve failed workspaces and allow successful workspaces to be removed after artifacts are written.

### R4 — Agent loop

- Send the system instruction, task prompt, conversation, available checks, budgets, and tool definitions to the model adapter.
- Accept assistant messages and structured tool calls.
- Continue until the agent invokes `finish`, returns a terminal response, the context is cancelled, or a budget is exhausted.
- Enforce limits for wall time, turns, model calls, tool calls, check calls, output bytes, and child-agent calls.
- Return malformed or denied tool calls as structured errors and record them in the trace.
- A budget expiration freezes and grades the current workspace rather than discarding it.

### R5 — File tools

Expose:

- `list_files`: list workspace-relative files with optional glob and result limit.
- `read_file`: read a UTF-8 text file with optional line range and byte limit.
- `search`: search workspace text with bounded results.
- `write_file`: create or replace a UTF-8 text file.
- `apply_patch`: apply a unified diff to one or more workspace files.
- `finish`: submit the current workspace and stop the agent loop.

`apply_patch` receives a standard unified diff containing target paths, context lines, removed lines, and added lines. It validates every target, applies matching hunks, and reports a conflict when the patch no longer matches the file.

All file tools must:

- accept workspace-relative paths only;
- reject absolute paths, `..` escapes, and symlink traversal outside the workspace;
- enforce per-call and per-run size limits;
- prevent access to hidden graders and evaluator artifacts;
- protect `go.mod`, `go.sum`, and test files that existed in `starter/`;
- allow the agent to create new test files, unless a future task policy explicitly forbids it.

### R6 — Named check tool

Expose `run_check` instead of a Go-specific `run_tests` tool:

```json
{"profile": "test"}
```

The public name maps to a fixed command generated by the built-in Go profile:

```yaml
test:
  command: ["go", "test", "-count=1", "-json", "./..."]
  parser: go_test_json
  timeout_seconds: 45
```

The agent selects only a public profile name. It cannot supply the executable, arguments, working directory, environment, parser, or timeout.

Every check must:

- run in the task workspace;
- enforce a timeout and terminate the process group on expiry;
- cap stdout and stderr and mark truncation;
- use an explicit environment allowlist plus non-secret values generated by the language profile;
- return exit code, duration, timeout status, parsed cases when available, and bounded output;
- record the argument vector and environment key names without secret values.

The universal result parser is `exit_code`. The MVP also implements `go_test_json`. Later parsers can support JUnit XML, TAP, or another versioned result protocol.

### R7 — Hidden tests and independent grading

- Hidden source is stored under the task's `hidden/` directory, never under `starter/`.
- Hidden files are absent from the agent workspace during the agent loop.
- After the workspace freezes, copy each hidden overlay into its corresponding workspace path.
- For example, `hidden/cache/cache_hidden_test.go` becomes `workspace/cache/cache_hidden_test.go`.
- The agent cannot invoke hidden profiles or receive hidden grader output.
- The Go profile supplies the final grader command as a fixed argument array; shell parsing is forbidden.
- Final grading reruns visible behavior as appropriate and includes hidden tests.
- Parse `go test -json` into package and test-case results.
- Record each grader group as passed, failed, timed out, setup error, or grader error.
- Mark a task solved only when every required grader passes and no protected-file policy is violated.
- Grade the final workspace even when the agent times out or exhausts its budget.

Hidden tests must map to requirements stated in the prompt. They may cover edge cases, error behavior, regressions, concurrency, public API compatibility, and hard-coded visible examples. They must not introduce unstated requirements.

### R8 — Code-quality evaluation

Correctness and code quality are separate results.

Always-run mechanical checks for the Go MVP:

- `gofmt` reports no unformatted Go files.
- `go vet ./...` passes.
- Protected files and required public APIs remain intact.
- No undeclared dependencies are added.
- Task-specific checks such as `go test -race` run when declared.

These checks produce a separate quality result. They do not affect `SOLVED` unless the task prompt explicitly makes a property part of the functional contract. Protected-file and dependency-policy violations invalidate the submission because they violate evaluation rules rather than style preferences.

Formatting and readability checks evaluate only starter files and files created or changed by the agent. Evaluator-injected hidden files are excluded from quality scoring.

An optional future LLM reviewer may score naming, readability, idiomatic Go, simplicity, error handling, and maintainability from 0–2 each. It receives the task prompt, final patch, relevant source, and deterministic results, and returns structured JSON with file and line evidence for deductions. Source and comments are treated as untrusted input. The judge model, settings, prompt version, and rubric version are recorded.

Use the same rubric for human review, and calibrate any future LLM reviewer against a small human-scored set of good, average, and poor solutions. An LLM quality score is qualitative metadata. It does not decide whether the task is solved and is not required for the two-day MVP.

### R9 — Multi-agent workflow compatibility

Here, a multi-agent workflow means a supervisor/sub-agent structure:

- one primary agent owns the task and final submission;
- the primary may delegate a bounded instruction to a child agent;
- the child returns findings or changes to the primary;
- workflow budgets cover all agents;
- traces record agent IDs, parent relationships, spans, calls, tokens, and tool use.

The required MVP executes one primary agent. The stretch implementation adds `delegate` with `{role, instruction, max_turns}` and limits it to two sequential children, no recursion, one shared workspace, child writes disabled by default, and no peer messaging or concurrent writes.

### R10 — Artifacts and reporting

Each run creates:

```text
<out>/<run-id>/
  run.json
  summary.json
  trace.jsonl
  tasks/<task-id>/result.json
  tasks/<task-id>/final.patch
  tasks/<task-id>/workspace/     # retained according to policy
```

- Write JSONL incrementally so interrupted runs remain inspectable.
- Atomically replace completed summary files.
- `report` reads artifacts without rerunning models or checks.
- Terminal output shows outcome, solved count, correctness, mechanical quality, duration, calls, tokens when known, and artifact path.
- Do not represent unavailable usage as zero.

## 6. Outcome model

Store three separate fields so execution state is not confused with solution correctness:

```text
attempt_status:
  COMPLETED       grading finished normally
  SETUP_ERROR     a required local tool or dependency was unavailable
  GRADER_ERROR    the evaluator could not execute or interpret the grader
  CANCELLED       the user interrupted the attempt

agent_stop_reason:
  FINISH_TOOL
  TERMINAL_RESPONSE
  BUDGET_EXHAUSTED
  MODEL_ERROR
  CANCELLED

grade_status:
  SOLVED          all required correctness graders passed
  UNSOLVED        grading ran and a required correctness grader failed
  NOT_GRADED      no valid grade was produced
```

A budget-exhausted or model-error attempt still freezes and grades its current workspace when possible. It may therefore be `COMPLETED`, `BUDGET_EXHAUSTED`, and `SOLVED` at the same time. Attempts with `SETUP_ERROR`, `GRADER_ERROR`, or `NOT_GRADED` are excluded from the solve-rate denominator.

## 7. Non-functional requirements

- Build and run on macOS and Linux with Go 1.23+.
- Require no runtime service other than the configured model API.
- Continue after a normal task, agent, or grader failure.
- Propagate cancellation through model calls, tools, checks, and graders.
- Use UTC RFC 3339 timestamps with nanoseconds and integer millisecond durations.
- Version manifests, traces, results, and optional judge rubrics.
- Redact configured secrets and authorization headers.
- Bound in-memory subprocess, model, and tool output.
- Produce deterministic grading for identical files and environments, excluding timing.
- Document that local execution runs trusted task code with the user's OS permissions.

## 9. Architecture

```text
CLI
 └─ SuiteRunner
     ├─ TaskLoader
     ├─ ProfileCompiler ── simple YAML -> normalized TaskSpec
     ├─ EnvironmentChecker
     ├─ ExecutionBackend ── LocalBackend now; ContainerBackend later
     ├─ WorkspaceManager
     ├─ WorkflowRunner
     │   ├─ ModelClient
     │   ├─ ToolRegistry ── file/search/patch/check/finish[/delegate]
     │   ├─ Budget
     │   └─ TraceSink
     ├─ Grader
     │   ├─ CheckRunner
     │   └─ ResultParsers ── exit_code, go_test_json
     ├─ QualityEvaluator
     └─ Reporter
```

The author-facing schema stays small. `ProfileCompiler` applies Go conventions and creates the explicit commands, parsers, paths, timeouts, and policies used by the runtime. Provider responses never execute processes or touch files directly. Tools use a task-scoped validated workspace and budget. Hidden graders remain outside the agent tool registry.

Extension seams:

- Other languages add environment probes, default profiles, and result parsers. `exit_code` works without a language-specific parser.
- Containers or remote workers add another `ExecutionBackend`.
- A web UI consumes versioned artifacts or a future composite trace sink.
- A database adds artifact and trace sink implementations.
- Model providers add `ModelClient` adapters.
- Larger suites add worker pools and external artifact storage.
- Richer agent teams replace the workflow plan while retaining IDs, spans, budgets, tools, and grading.

## 10. Simplified author-facing schemas

### `suite.yaml`

```yaml
version: 1
id: go-core-v1
title: Go Core Tasks
language: go
toolchain: ">=1.23"

tasks:
  - config-parser
  - retry-package
  - fix-worker-leak
  - cache-ttl

defaults:
  timeout_seconds: 300
  max_turns: 20
  max_tool_calls: 60
  max_check_calls: 10
```

Required suite fields are `version`, `id`, `title`, `language`, `toolchain`, and `tasks`. `defaults` is optional and falls back to evaluator constants.

V1 keeps provider and safety limits such as maximum model calls, child agents, and captured bytes in evaluator configuration rather than repeating them in task manifests. The required MVP fixes `max_child_agents` at zero; the stretch delegate workflow introduces an explicit workflow-level setting later.

### `task.yaml`

```yaml
version: 1
id: retry-package
title: Implement a context-aware retry package
kind: generation
tags: [context, timing, errors]

budget:
  timeout_seconds: 240
  max_turns: 18

checks:
  race: false
```

Required task fields are `version`, `id`, `title`, and `kind`. `tags`, `budget`, and `checks` are optional. Omitting all optional fields is valid.

The task directory supplies the remaining information by convention:

```text
tasks/retry-package/
  task.yaml       metadata and exceptional overrides
  prompt.md       requirements shown to the agent
  starter/        initial workspace copied for each attempt
  hidden/         final-test overlay, absent during agent work
  reference/      known-good solution used only to validate the task
```

The Go profile supplies these defaults:

| Concern | Convention | Timeout |
|---|---|---:|
| Dependency files | `go.mod`, `go.sum` | — |
| Preparation | `go mod download`, then `go mod verify` | 120s / 30s |
| Compile check | `go test -run ^$ ./...` | 60s |
| Public `test` check | `go test -count=1 -json ./...` | 45s |
| Final behavior grader | Install `hidden/`, then run the public test command again | 60s |
| Result parser | `go_test_json` | — |
| Quality | in-process `gofmt` comparison and `go vet ./...` | 30s for vet |
| Protected files | `go.mod`, `go.sum`, and test files present in the initial starter | — |
| New tests | Agent-created test files are allowed | — |
| Preflight | Starter fails the behavior grader; reference solution passes | profile checks |

`checks.race: true` adds `go test -race -count=1 ./...`. `checks.packages` may override the default `./...` selector for the unusual task that needs a narrower package scope. Budget fields omitted from `task.yaml` inherit suite defaults.

The loader expands the small manifests into a normalized internal `TaskSpec`. That plan contains the full workspace rules, argument arrays, parsers, timeouts, graders, quality checks, and budgets used by the runtime. Generated commands are executed directly without shell parsing. `run.json` includes the normalized plan and its content hash so a result remains auditable.

Validation rules:

- IDs match `[a-z0-9][a-z0-9-]{1,63}`.
- A suite task ID must match its directory name and the ID in `task.yaml`.
- `kind` is one of `generation`, `repair`, or `feature` in v1.
- `prompt.md`, `starter/`, `hidden/`, `reference/`, `go.mod`, and `go.sum` exist for every shipped MVP task.
- Convention paths resolve inside the task directory and hidden overlay targets resolve inside the workspace.
- Package selectors match a conservative pattern such as `./...` or `./internal/foo/...`.
- Task budget overrides remain within evaluator-wide hard caps.
- Unknown versions and fields are rejected in strict mode.

## 11. Proposed evaluation suite

| Task | Category | Agent work | Hidden coverage |
|---|---|---|---|
| `config-parser` | Code generation | Implement typed JSON parsing and validation from a specification | Missing or wrong fields, bounds, unknown fields, malformed input, useful errors |
| `retry-package` | Code generation | Implement a context-aware retry API from declarations and docs | Cancellation, attempt counts, capped delay, invalid policy, no final wait |
| `fix-worker-leak` | Bug repair | Diagnose and repair a small worker pool | Cancellation, error exit, closed channels, fewer jobs than workers, blocked sends |
| `cache-ttl` | Feature extension | Add TTL behavior to an existing cache without regressions | Expiry, refresh, capacity interactions, deterministic clock, existing behavior |

Task design rules:

- Keep starter code under roughly 300 lines unless navigation is part of the task.
- State every graded behavior in the prompt.
- Provide visible tests for basic feedback and hidden tests for unexposed cases.
- Avoid external network access, cgo, large dependencies, and sleep-based timing.
- Inject clocks or synchronization signals for deterministic time and concurrency tests.
- Include a reference solution used only by suite validation.
- Include at least two code-generation tasks and at least one repair task.

## 12. Go interfaces

```go
type ModelClient interface {
    Generate(ctx context.Context, req ModelRequest) (ModelResponse, error)
}

type ProfileCompiler interface {
    Compile(suite SuiteConfig, task TaskConfig) (TaskSpec, error)
}

type Tool interface {
    Name() string
    Schema() json.RawMessage
    Execute(ctx context.Context, tc ToolContext, args json.RawMessage) ToolResult
}

type WorkflowRunner interface {
    Run(ctx context.Context, spec WorkflowSpec, tc TaskContext) (WorkflowResult, error)
}

type ExecutionBackend interface {
    Prepare(ctx context.Context, task TaskSpec, runDir string) (Workspace, error)
    Run(ctx context.Context, ws Workspace, cmd CommandSpec) (ProcessResult, error)
    Close(ctx context.Context, ws Workspace) error
}

type ResultParser interface {
    Name() string
    Parse(result ProcessResult) (CheckResult, error)
}

type Grader interface {
    Grade(ctx context.Context, task TaskSpec, ws Workspace) (GradeResult, error)
}

type TraceSink interface {
    Emit(ctx context.Context, event TraceEvent) error
    Close() error
}

type ArtifactStore interface {
    WriteRun(ctx context.Context, result RunResult) error
    WriteTask(ctx context.Context, result TaskResult) error
}
```

`Generate` means “produce the model's next turn,” which may be a message, tool call, or terminal response. It does not mean the coding task is complete.

```go
type ToolContext struct {
    RunID, TaskID, AgentID string
    WorkspaceRoot          string
    Budget                 *Budget
    PublicChecks           map[string]CheckSpec
}

type CommandSpec struct {
    Program   string
    Args      []string
    Dir       string
    Env       map[string]string
    Timeout   time.Duration
    MaxOutput int64
}

type CheckResult struct {
    Status    CheckStatus
    ExitCode  int
    TimedOut  bool
    Duration  time.Duration
    Cases     []CaseResult
    Output    string
    Truncated bool
}
```

Every trace event contains schema version, sequence, timestamp, run ID, trace ID, event type, payload, and optional task, agent, parent-agent, span, and parent-span IDs.

V1 event types:

- `run.started`, `run.finished`
- `environment.started`, `environment.finished`, `environment.error`
- `task.started`, `task.frozen`, `task.finished`
- `agent.started`, `agent.message`, `agent.finished`
- `model.request`, `model.response`, `model.error`
- `tool.started`, `tool.finished`, `tool.denied`
- `check.started`, `check.finished`
- `grader.started`, `grader.case`, `grader.finished`
- `quality.finished`
- `budget.exhausted`, `error`

Large output is truncated with original byte count and a truncation flag. Credentials and authorization headers are never serialized.

## 13. CLI contract

```text
agent-eval doctor --suite tasks/suite.yaml [--check-model]
agent-eval list   --suite tasks/suite.yaml
agent-eval run    --suite tasks/suite.yaml [--task ID ...]
                     [--model NAME] [--out DIR] [--parallel N]
                     [--keep-workspaces] [--fail-on-unsolved]
agent-eval report RUN_DIR [--json]
```

Configuration precedence is flags, environment variables, then manifest defaults.

Environment variables:

- `AGENT_EVAL_API_KEY`
- `AGENT_EVAL_BASE_URL` for a non-default endpoint
- `AGENT_EVAL_MODEL` unless supplied by flag

Exit codes:

- `0`: evaluation completed; unsolved tasks are allowed unless requested otherwise.
- `1`: configuration, setup, grader, or infrastructure failure.
- `2`: evaluation completed with unsolved tasks and `--fail-on-unsolved` was set.
- `130`: interrupted.

## 14. Grading and metrics

### Correctness

```text
task_score = passed grader weight / total grader weight
solve_rate = solved tasks / gradable tasks
weighted_score = sum(task_score × task weight) / sum(task weight)
```

The diagnostic task score may grant partial credit. `SOLVED` remains strict: every required grader passes. Setup and grader infrastructure failures are reported outside the solve-rate denominator.

### Quality

Report formatting, static analysis, race checking when applicable, dependency-policy compliance, protected-file compliance, and any future LLM rubric score separately from correctness.

### Efficiency

- Task and total wall time.
- Environment preparation time.
- Model calls, turns, and tool calls.
- Prompt, completion, and total tokens when reported.
- Check invocations and cumulative duration.
- Approximate cost only with an explicit local price table.
- Files changed, lines added, and lines removed.

### Reliability and behavior

- Outcome and failure stage.
- Model, tool, and grader errors.
- Tool denial rate and budget-exhaustion reason.
- First public-check pass turn and time.
- Per-agent calls and tokens when delegation is enabled.
- Environment fingerprint and preparation result.

For single attempts, report pass at one. A future repetition option reports success rate, median score, median time, and median tokens. Do not combine correctness, quality, and efficiency into one opaque score.

## 15. Test plan for `agent-eval`

### Unit tests

- YAML decoding, strict validation, and default merging.
- Go-profile expansion from small manifests into a normalized `TaskSpec`, including default and overridden package selectors.
- Version constraints and environment error classification.
- Workspace containment for absolute paths, `..`, symlinks, and prefix-confusion paths.
- Starter copying, hidden overlays, protected files, and fixture hashing.
- Protection of starter test files while permitting new agent-authored test files.
- File limits and unified-patch success and conflicts.
- Named-check lookup and rejection of unknown or hidden check names.
- Command construction that prevents shell syntax and agent-selected arguments.
- Budget accounting at exact boundaries.
- Trace sequences, truncation, and redaction.
- `exit_code` and `go_test_json` parsing for pass, fail, build failure, timeout, and malformed output.
- Score aggregation, required-check semantics, status fields, and exit codes.

### Integration tests

- A scripted model reads, patches, runs a public check, and finishes with a passing grade.
- An incorrect scripted model receives `UNSOLVED`.
- A budget-limited model has its frozen workspace graded and records both its stop reason and grade status.
- Malformed calls, denied paths, model errors, cancellation, timeouts, and output overflow are traced.
- Hidden files appear only after `task.frozen`.
- The canonical starter remains byte-for-byte unchanged.
- A missing tool or failed dependency preparation produces `SETUP_ERROR` without model use.
- An interrupted run leaves parseable JSONL.

### Task-suite validation

For every task:

- Dependency preparation succeeds in supported environments.
- The starter has its documented initial state.
- Visible checks provide useful but incomplete feedback.
- Hidden tests reject the starter and accept the reference solution.
- Every hidden assertion maps to a written requirement.
- Formatting, vet, and race checks succeed on the reference solution.
- Tests avoid undeclared network, system, and timing dependencies.

### End-to-end acceptance

Using one configured real model:

- `doctor` declares the suite ready.
- `list` displays all tasks and categories.
- A selected task emits every documented artifact.
- `report` reproduces the result without model or network access.
- Scripted passing and failing solutions prove grading is independent of the agent's claim.
- No agent tool can read outside its workspace or invoke an arbitrary command.

## 16. Definition of done

- The CLI builds with Go 1.23+.
- `doctor`, `list`, `run`, and `report` work from a clean checkout.
- At least three Go tasks ship, including code generation and repair.
- A real model can edit a fresh workspace and run named public checks.
- Hidden overlays appear only after the workspace freezes.
- Grading produces deterministic correctness and mechanical quality results.
- Setup and grader errors are distinguished from unsolved tasks.
- Versioned traces and results cover success, failure, budget exhaustion, and interruption.
- Workspace containment, command control, and hidden boundaries have dedicated tests.

## 18. Scaling beyond the MVP

### Additional languages

Tasks remain declarative:

```yaml
version: 2
id: python-core-v1
title: Python Core Tasks
language: python
profile: pytest
toolchain: ">=3.12,<3.13"
tasks:
  - retry-package
```

A future Python profile expands this suite and the same small task manifests into virtual-environment setup, locked dependency installation, `pytest`, formatting, linting, and result parsing. File tools, workflows, hidden overlays, traces, grading, and reporting remain unchanged. A language profile can begin with the universal `exit_code` parser; richer reporting comes from parsers such as JUnit XML.

Local dependency isolation can use Python virtual environments, workspace-local Node modules, Go caches, or Rust cache directories. These do not isolate the operating system or untrusted processes.

### Container execution

Add `ContainerBackend` behind `ExecutionBackend`. A production backend should use a fixed toolchain image, unprivileged user, read-only base filesystem, writable temporary workspace, disabled evaluation-time networking, dropped capabilities, resource limits, and one container lifetime per attempt.

The suite and language profile declare environment requirements; evaluator configuration chooses how to provide them. Tasks do not hard-code `local` or `container` execution.

### UI and storage

A future UI consumes versioned results and traces. Databases or object stores are added through `ArtifactStore` and `TraceSink`. Neither changes execution or grading.

## 19. Tradeoffs and deferred decisions

- Hidden tests are concealed from the agent process, not from the human who owns the repository.
- Local checks execute trusted task code with the user's OS permissions.
- Virtual environments and caches isolate dependencies but do not provide a security boundary.
- Exact machine reproduction is deferred until a container or managed backend exists.
- Profile-generated commands and parser interfaces support future languages; the MVP validates only Go tasks.
- Mechanical checks provide repeatable quality signals. Naming and readability require human or LLM judgment and remain a separate optional score.
- An LLM judge may vary and can be influenced by submitted text; it never determines correctness.
- JSONL is the detailed history; summary JSON is derived.
- Parallel writes by multiple agents are deferred.
- Missing provider usage remains unknown rather than zero.
